# 多 ROI 区域裁剪推理及结果融合方案

## 1. 文档信息

| 项目 | 内容 |
| --- | --- |
| 文档版本 | V1.1 |
| 文档状态 | 研发评审稿 |
| 适用模型 | EV-VLM |
| 适用范围 | 普通视觉分析、多 ROI 分析、`bbox_2d` 坐标检测 |
| 调用协议 | OpenAI Chat Completions 兼容协议 |

## 2. 需求背景

当前平台调用视觉语言大模型时，请求中包含：

- 原始整张图片；
- 提示词；
- 模型推理参数。

算法服务将整图送入 vLLM 推理，并通过 OpenAI 兼容接口，将模型输出放入以下字段返回平台：

```text
choices[0].message.content
```

现有普通分析及 `bbox_2d` 坐标检测均已支持整图模式。

现需要增加多矩形 ROI 能力：

1. 平台在整图上绘制 0～N 个矩形 ROI；
2. 平台将原图、公共提示词及 ROI 的 WKT 坐标发送给算法服务；
3. 算法服务按 ROI 裁剪原图，每个 ROI 独立调用一次模型；
4. 每次调用使用相同提示词和推理参数；
5. 算法服务融合各 ROI 输出后，通过原接口返回平台；
6. 对包含 `bbox_2d` 的结果，必须将裁剪图局部坐标转换为原图坐标；
7. 平台继续使用现有关键词检测、报警和 2D 框渲染机制。

## 3. 方案结论摘要

本方案在平台与 vLLM 之间增加 **ROI 调度适配层**，由算法侧实现，不修改大模型本身。

核心策略如下：

- 对外保持现有接口兼容，仅增加可选的 `roi_wkt_list` 字段；
- 0 个 ROI 时，完全沿用现有整图推理链路；
- N 个 ROI 时，从同一张原图裁剪 N 张图片，分别调用模型；
- 多个 ROI 支持受控并发，结果按平台传入顺序排列；
- 普通文本结果采用确定性原文拼接，不调用大模型二次总结；
- 任一 ROI 命中报警关键词，平台即判定整体报警；
- 坐标结果先转换到原图坐标系，再按 ROI 分隔符分段返回，每段保留独立的坐标 JSON 数组；
- 不做跨 ROI 去重、NMS、目标关联或多数投票；
- 推理失败的 ROI 不得静默当作“无目标”或“未报警”。

> 异常处理目前建议默认采用“有限重试后，任一 ROI 失败则整请求失败”。如业务必须支持部分结果返回，需要平台同步识别“结果不完整”状态后再启用。

## 4. 建设目标

### 4.1 兼容性目标

- 对外继续使用现有模型服务接口，不新增平台调用地址。
- 请求主体继续使用现有 OpenAI 兼容格式，仅增加可选 ROI 字段。
- 当 ROI 数量为空时，必须完全走现有整图推理链路，请求和响应行为不变。
- 当 ROI 数量大于 0 时，仍只返回一个 `choices[0].message.content`，平台无需按多个 Choice 处理。
- 普通文本结果继续支持平台关键词检测。
- 坐标结果继续支持平台现有 `bbox_2d` 检测和渲染。

### 4.2 功能目标

- 支持 0～N 个轴对齐矩形 ROI。
- 支持多个 ROI 独立、并行推理。
- 支持普通文本结果的无损拼接。
- 支持坐标结果按 ROI 分段输出及原图坐标转换。
- 支持 ROI 顺序、执行状态、错误和耗时的可追踪性。

### 4.3 本期不做的处理

- 不调用大模型对多个 ROI 结果进行二次总结或改写；
- 不做跨 ROI 语义去重；
- 不做跨 ROI 目标去重、NMS、目标跟踪或 ID 关联；
- 不根据“多数 ROI 的结果”进行投票；
- 不用后面的 ROI 结果覆盖前面的 ROI 结果；
- ROI 数量大于 0 时，不额外对整图再做一次推理；
- 本期不支持每个 ROI 使用不同提示词，所有 ROI 共用请求中的同一个提示词。

## 5. 整体处理链路

```text
上层平台
   │
   │ 原图 + 提示词 + 推理参数 + 可选 ROI WKT 列表
   ▼
ROI 调度适配层（算法侧新增）
   │
   ├─ 0 个 ROI：直接走原有整图推理链路
   │
   └─ N 个 ROI：
        1. 解码原图
        2. 校验并解析 WKT
        3. 裁剪 N 张 ROI 图片
        4. 分别构造 N 个内部模型请求
        5. 并发调用现有 vLLM 服务
        6. 收集并按 ROI 输入顺序排序
        7. 普通文本拼接，或坐标转换后按 ROI 分段
        8. 构造一个 OpenAI 兼容响应
   ▼
上层平台
   │
   ├─ 按现有关键词规则判断是否报警
   └─ 按现有 bbox_2d 规则渲染检测框
```

ROI 调度适配层必须在内部调用 vLLM 前移除自定义 ROI 字段，避免 vLLM 因无法识别扩展字段而报错。

## 6. 请求协议

### 6.1 新增字段

在现有请求顶层增加可选字段 `roi_wkt_list`：

```json
{
  "roi_wkt_list": [
    "POLYGON ((100 80, 500 80, 500 420, 100 420, 100 80))",
    "POLYGON ((600 100, 900 100, 900 500, 600 500, 600 100))"
  ]
}
```

完整请求示意：

```json
{
  "messages": [
    {
      "role": "user",
      "content": [
        {
          "text": "原有提示词，原样应用于每一个ROI",
          "type": "text"
        },
        {
          "image_url": {
            "url": "data:image/jpeg;base64,<原始整图Base64>"
          },
          "type": "image_url"
        }
      ]
    }
  ],
  "model": "EV-VLM",
  "stream": false,
  "enable_thinking": false,
  "max_tokens": 2048,
  "presence_penalty": 0.0,
  "temperature": 0.0,
  "top_p": 0.7,
  "roi_wkt_list": [
    "POLYGON ((100 80, 500 80, 500 420, 100 420, 100 80))",
    "POLYGON ((600 100, 900 100, 900 500, 600 500, 600 100))"
  ]
}
```

> 实际请求结构应以现有接口为准：当前示例中 `type: "image_url"` 与 `image_url` 对象同级，研发实现和联调示例不得改变现有消息结构。

### 6.2 ROI 数量约定

以下三种情况均表示 0 个 ROI：

```json
{}
```

```json
{
  "roi_wkt_list": null
}
```

```json
{
  "roi_wkt_list": []
}
```

处理要求：

- 0 个 ROI：原图直接推理，响应保持现有格式和行为；
- 1 个 ROI：裁剪一张图片推理；
- N 个 ROI：裁剪 N 张图片，分别推理；
- 最大 ROI 数量应支持服务配置，超过限制时返回参数错误，不得静默丢弃多余 ROI；
- 重复 ROI、重叠 ROI 均允许，默认不去重、不合并。

### 6.3 WKT 格式及坐标约定

本期每个 ROI 使用一个 `POLYGON` 表示一个轴对齐矩形。

要求：

1. 多边形必须闭合，共 5 个坐标点，首尾点相同；
2. 只支持矩形，不支持任意四边形、旋转矩形、任意多边形或 `MULTIPOLYGON`；
3. 矩形的边必须与图像坐标轴平行；
4. 坐标基于原始整图，而不是平台显示缩放后的图片；
5. 坐标原点为图像左上角，`x` 向右增大，`y` 向下增大；
6. 坐标定义为边界坐标，不是像素索引：左、上边界为闭区间，右、下边界为开区间，因此 `x2` 可以等于图像宽度，`y2` 可以等于图像高度；
7. ROI 必须位于原图范围内，并满足：

```text
0 ≤ x1 < x2 ≤ 原图宽度
0 ≤ y1 < y2 ≤ 原图高度
```

8. 建议平台直接传整数像素坐标。若传入浮点数，`x1、y1` 向下取整，`x2、y2` 向上取整，确保裁剪区域完整覆盖平台绘制的 ROI；
9. 图像解码及 EXIF 方向处理必须复用现有整图链路，平台画框与算法裁剪必须使用同一图像方向和同一坐标基准。

以下情况返回 HTTP 400 参数错误：

- WKT 无法解析；
- 多边形未闭合；
- 不是轴对齐矩形；
- ROI 面积为空；
- ROI 超出原图范围；
- ROI 数量超过服务限制。

## 7. ROI 裁剪与模型调用

### 7.1 裁剪要求

对于第 `i` 个 ROI，解析得到：

```text
roi_i = [roi_x1, roi_y1, roi_x2, roi_y2]
```

裁剪结果必须满足：

```text
crop_i = 原图[roi_y1:roi_y2, roi_x1:roi_x2]
```

同时保存以下信息，供后续坐标转换使用：

```text
roi_x1、roi_y1
crop_width  = roi_x2 - roi_x1
crop_height = roi_y2 - roi_y1
```

所有 ROI 必须从同一份解码后的原图裁剪，不得将前一个 ROI 的裁剪结果作为后一个 ROI 的输入。

### 7.2 内部模型请求

每个 ROI 构造一个独立的内部请求：

- 复制原始请求中的提示词；
- 复制原始请求中的模型名称和推理参数；
- 将 `image_url` 中的整图替换为当前 ROI 的裁剪图；
- 删除 `roi_wkt_list`；
- 不把 WKT 坐标额外拼入提示词；
- 不修改提示词内容；
- 不因为 ROI 数量增加而修改 `temperature`、`max_tokens` 等参数。

每个 ROI 的实际模型输入为：

```text
同一份提示词 + 当前 ROI 的裁剪图片
```

### 7.3 并发及顺序

- 多 ROI 请求应支持并发执行，并设置可配置的最大并发数，避免瞬间打满 vLLM；
- 最终结果必须按照平台传入的 ROI 顺序排列，不得按照推理完成先后排列；
- 每个内部请求必须绑定请求 ID 和 ROI 下标，防止并发场景下结果串位；
- 本期多 ROI 仅支持 `stream=false`，如收到多 ROI 流式请求，返回明确的暂不支持错误；
- 0 ROI 的原有调用方式不受影响。

## 8. 普通文本结果融合

### 8.1 基本策略

普通分析结果采用 **确定性原文拼接**，不增加大模型二次总结。

处理要求：

- 保留每个 ROI 的模型原始输出；
- 只允许移除首尾无意义空白，不得删除或改写正文；
- 不合并 `is_alert` 字段；
- 不删除其他 ROI 的 `false`、报警描述或关键词；
- 不进行多数投票；
- 不进行语义润色、归纳或缩写。

### 8.2 拼接格式

单个 ROI 时，`content` 直接返回该 ROI 的原始文本，不额外添加标记。

多个 ROI 时，使用固定格式：

```text
<<<ROI_1>>>
第1个ROI的模型原始输出

<<<ROI_2>>>
第2个ROI的模型原始输出

<<<ROI_3>>>
第3个ROI的模型原始输出
```

要求：

- ROI 编号从 1 开始，与请求顺序一致；
- 分隔符固定，便于平台后续需要时拆分；
- 分隔符中不得包含 `alert`、`alarm`、`is_alert`、`bbox_2d` 以及具体业务报警关键词，避免干扰平台检测；
- 即使某个 ROI 输出为空，也保留其 ROI 标记，不得直接丢弃。

### 8.3 报警兼容要求

算法侧不额外生成一个汇总结论，平台仍对融合后的完整 `content` 执行现有报警检测。

平台侧必须遵循：

1. 对完整文本进行检查，而不是只检查最后一个 ROI；
2. 任一 ROI 命中报警关键词，整次请求即判定报警；
3. 正向报警命中优先于其他 ROI 的未报警文本；
4. 不得因为结果中同时存在 `false`，就覆盖已经命中的报警结果；
5. 只有请求完整成功且所有 ROI 均未命中报警条件时，才按未报警处理。

例如：

```text
<<<ROI_1>>>
{"is_alert": false}

<<<ROI_2>>>
{"is_alert": true}
```

平台应将整体判定为报警。

如果某些应用场景并非“全文关键词检索”，而是只能解析单个 JSON 对象，则这些场景需要平台同步适配，不能直接套用上述多 ROI 文本拼接格式。

## 9. 坐标结果处理

### 9.1 支持的坐标格式

本期必须支持现有 REC 格式：

```json
[
  {
    "bbox_2d": [100, 200, 300, 400],
    "label": "目标名称"
  }
]
```

同时允许模型输出被 Markdown JSON 代码块包裹，适配层应先按现有规则去除代码块再解析。

无目标时：

```json
[]
```

如果同一提示词下的部分 ROI 返回坐标数组、部分 ROI 返回普通文本，或者部分 ROI 的坐标结果无法解析，应返回结果处理错误，不能把混合结果直接拼接返回。

### 9.2 局部坐标转换为原图坐标

模型在某个 ROI 裁剪图中返回：

```text
bbox_local = [local_x1, local_y1, local_x2, local_y2]
```

若该坐标已经是以裁剪图像素为单位的坐标，则转换为：

```text
global_x1 = local_x1 + roi_x1
global_y1 = local_y1 + roi_y1
global_x2 = local_x2 + roi_x1
global_y2 = local_y2 + roi_y1
```

示例：

```text
原图 ROI：[100, 200, 500, 600]
裁剪图尺寸：400 × 400

模型输出局部框：
[20, 30, 120, 230]

返回平台的原图框：
[120, 230, 220, 430]
```

### 9.3 模型内部缩放的坐标处理

如果模型输出的坐标不是基于裁剪图原始像素，而是基于模型内部 Resize 后的图像或归一化坐标，则不得直接加 ROI 偏移。

必须按以下顺序处理：

```text
模型输出坐标
→ 复用现有整图 REC 坐标后处理规则
→ 还原为当前裁剪图原始像素坐标
→ 加上 ROI 的 x、y 偏移
→ 得到原图坐标
```

换算关系为：

```text
local_x = model_x × crop_width  / model_coord_space_width
local_y = model_y × crop_height / model_coord_space_height
```

然后再加 `roi_x1、roi_y1`。

其中，`model_coord_space_width/height` 必须根据现有模型实际坐标定义确定，不能凭空假定为原图尺寸或 1000。

### 9.4 坐标后处理要求

- 转换后的框应限制在当前 ROI 及原图有效范围内；
- 对转换后面积为空或坐标顺序非法的框，应丢弃并记录日志；
- 需要取整时，左上角向下取整、右下角向上取整，避免缩小检测框；
- `label` 及其他已有字段原样保留；
- 为保持平台兼容，本期不在 `content` 的检测对象中额外增加 `roi_index` 等字段；
- 重叠 ROI 中重复检出的目标，本期不做跨 ROI 去重或 NMS；
- 不得把任何未经转换的局部坐标直接返回平台。

### 9.5 多 ROI 坐标结果分段输出

为与普通文本结果保持统一的融合方式，多个 ROI 均返回合法坐标数组时，最终 `content` 也使用 ROI 分隔符分段。每个 ROI 分段内保留独立的坐标 JSON 数组，不再将所有 ROI 的坐标数组合并为一个数组。

示例：

```text
<<<ROI_1>>>
[{"bbox_2d":[120,230,220,430],"label":"卷帘门前人员"}]

<<<ROI_2>>>
[]

<<<ROI_3>>>
[{"bbox_2d":[680,180,760,410],"label":"卷帘门前人员"}]
```

分段规则：

1. 按 ROI 输入顺序依次输出，ROI 编号从 1 开始；
2. 必须先将当前 ROI 的局部坐标全部转换为原图坐标，再写入对应分段；
3. 同一 ROI 内保持模型原始目标顺序；
4. 无目标的 ROI 必须保留对应分段，并在分段内返回 `[]`，不得直接省略该 ROI；
5. 所有 ROI 均无目标时，仍返回全部分段，每个分段的内容均为 `[]`；
6. 各分段内的坐标数组不得添加 Markdown 代码块或额外解释文字；
7. 单个坐标 ROI 时，直接返回转换后的纯 JSON 数组，不增加分隔符；0 ROI 时保持现有整图响应不变；
8. 不做跨 ROI 数组合并、目标去重或 NMS。

**平台解析要求：**加入分隔符后，多 ROI 坐标模式下的完整 `content` 是包含多个独立 JSON 数组的文本，不再是一个可整体解析的 JSON 数组。这不会影响 OpenAI 接口结构，因为 `content` 本身仍为字符串，但平台必须同步满足以下要求：

- 按 ROI 分隔符拆分后逐段解析，或对完整文本全局提取全部坐标结果；
- 不得只处理第一个 ROI、第一个 JSON 数组或第一个 `bbox_2d`；
- 不得直接对整个多 ROI `content` 执行单次 JSON 解析；
- 所有 ROI 分段均解析完成后，统一进行 2D 框渲染；
- 任一分段解析失败时，应明确标记异常，不得静默忽略该 ROI。

## 10. 响应协议

多 ROI 推理完成后，仍返回一个 OpenAI 兼容响应：

```json
{
  "id": "chatcmpl-<新请求ID>",
  "object": "chat.completion",
  "created": 1793961589,
  "model": "EV-VLM",
  "choices": [
    {
      "index": 0,
      "message": {
        "role": "assistant",
        "content": "<普通文本拼接结果，或按ROI分段的坐标JSON数组文本>"
      },
      "finish_reason": "stop"
    }
  ],
  "usage": {
    "prompt_tokens": 1200,
    "completion_tokens": 180,
    "total_tokens": 1380
  }
}
```

要求：

- `usage` 为所有 ROI 内部请求的用量之和；
- 所有 ROI 均正常结束时，`finish_reason` 为 `stop`；
- 任一 ROI 因 `max_tokens` 被截断时，整体 `finish_reason` 应为 `length`，并记录具体 ROI；
- 不将每个 ROI 放入不同的 `choices`；
- 0 ROI 时直接返回现有链路响应，不重新包装。

## 11. 异常处理

### 11.1 建议默认策略

ROI 推理经过有限重试后，只要仍有一个 ROI 失败，则整次请求返回失败，不得将失败 ROI 静默当作空结果或正常结果。

原因：

```text
推理失败 ≠ 没有目标 ≠ 没有报警
```

若将失败 ROI 按 `[]` 或空文本处理，平台可能将一次不完整的检测误判为“未报警”。

### 11.2 重试及错误信息

- 网络超时、连接异常、可重试的 5xx 错误可进行有限次数重试；
- 参数错误、WKT 错误等不可重试错误不得重复请求；
- 错误响应中应包含失败 ROI 的下标及失败原因；
- ROI 下标在错误和日志中统一从 0 开始，展示文本中的 ROI 编号从 1 开始。

示例：

```json
{
  "error": {
    "message": "ROI inference failed after retry",
    "type": "roi_inference_error",
    "code": "ROI_INFERENCE_FAILED",
    "roi_index": 1
  }
}
```

以下情况同样不得静默返回部分正常结果：

- 裁剪失败；
- 模型响应为空且不符合预期；
- 坐标 JSON 无法解析；
- 坐标任务与普通文本任务混杂；
- 坐标转换失败。

如后续业务确实需要“部分 ROI 成功也返回”，必须另行增加显式降级模式，并同时返回“结果不完整”状态及失败 ROI 列表；平台未完成配套识别前，不启用该模式。

## 12. 日志与可观测性

每次多 ROI 请求至少记录：

- 总请求 ID；
- 模型名称；
- ROI 数量；
- 每个 ROI 的下标和原图坐标；
- 每个 ROI 的裁剪尺寸；
- 每个 ROI 的内部请求 ID；
- 每个 ROI 的排队耗时、推理耗时及重试次数；
- 每个 ROI 的输出长度、检出框数量；
- 普通文本模式或坐标结果模式；
- 坐标解析及转换异常；
- 整体耗时和 Token 汇总；
- 失败 ROI 及错误原因。

日志中默认不记录完整 Base64 图片，避免日志体积过大及图像数据泄露。

## 13. 验收标准

| 编号 | 测试场景 | 预期结果 |
| --- | --- | --- |
| 1 | 不传 `roi_wkt_list` | 与现有整图调用一致 |
| 2 | `roi_wkt_list=null` 或 `[]` | 与现有整图调用一致 |
| 3 | 单个普通文本 ROI | 只裁剪一次、推理一次，返回原始文本 |
| 4 | 多个普通文本 ROI | 每个 ROI 均独立推理，结果按输入顺序拼接 |
| 5 | ROI 1 未报警、ROI 2 报警 | 两个原文均保留，平台整体判定报警 |
| 6 | 所有 ROI 均未报警 | 平台整体不报警 |
| 7 | ROI 1 报警、ROI 2 未报警 | 后面的未报警结果不得覆盖前面的报警 |
| 8 | 多个坐标 ROI | 按 ROI 分隔符分段返回，每段为独立 JSON 数组，坐标均为原图坐标 |
| 9 | 一个 ROI 返回 `[]`，另一个返回检测框 | 两个 ROI 分段均保留，空结果分段为 `[]`，另一分段包含检测框 |
| 10 | 所有坐标 ROI 返回 `[]` | 保留全部 ROI 分段，每个分段均为 `[]` |
| 11 | 已知局部框和 ROI 偏移 | 转换结果与人工计算完全一致 |
| 12 | ROI 为整张图片 | 与整图检测结果语义一致，坐标偏移为 0 |
| 13 | ROI 位于图像边缘 | 不越界、不出现宽高为 0 的裁剪图 |
| 14 | 重叠 ROI | 独立推理，不去重、不做 NMS |
| 15 | 非法 WKT、越界 ROI、零面积 ROI | 返回 HTTP 400，不调用模型 |
| 16 | 一个 ROI 推理失败 | 重试后整请求报错，不返回“无报警”结果 |
| 17 | 坐标结果与普通文本混杂 | 返回结果处理错误，不返回未转换坐标 |
| 18 | 多 ROI 并发完成顺序不同 | 返回结果仍按 ROI 输入顺序排列 |
| 19 | 带 EXIF 方向的 JPEG | 平台画框、算法裁剪及返回坐标方向一致 |
| 20 | 原请求包含不同推理参数 | 每个 ROI 请求均完整继承原参数 |
| 21 | 多个 ROI 分段均包含检测框 | 平台解析并渲染全部分段，不得只处理第一段或第一个检测框 |
| 22 | 单个坐标 ROI | 直接返回转换后的纯 JSON 数组，不增加 ROI 分隔符 |

## 14. 研发交付物

1. ROI 调度适配层及配置项；
2. 更新后的请求、响应接口说明；
3. WKT 校验和图像裁剪模块；

7. 错误处理、重试及日志能力；
8. 单元测试、接口测试和上述验收用例测试结果；
9. 一组平台可直接联调的请求／响应示例，至少包含：
   - 0 ROI；
   - 多 ROI 普通文本；
   - 多 ROI 中一个报警；
   - 多 ROI 坐标检测；
   - 单 ROI 推理失败。

## 15. 联调时需重点确认的事项

1. 平台当前报警逻辑是否确实为全文关键词检索，而非单个 JSON 对象解析；
2. 平台遇到多个 `is_alert` 时，是否保证任一正向报警命中即整体报警；
3. 当前 REC 模型输出坐标相对于哪个图像尺寸，是否经过内部 Resize 或归一化；
4. 平台画框坐标是否已经转换为原图像素坐标；
5. 平台与算法对 EXIF 图像方向的处理是否一致；
6. 服务允许的最大 ROI 数、并发数、单次请求超时及重试次数；
7. 是否接受本方案建议的“任一 ROI 失败则整请求失败”策略；
8. 如必须允许部分 ROI 失败，平台如何识别并展示“结果不完整”，避免误判为未报警；
9. 平台是否能够按 ROI 分隔符逐段解析，或全局提取全部 `bbox_2d`，而不是只处理第一个坐标结果；
10. 平台是否已取消对多 ROI 坐标 `content` 的整体单次数组解析，并完成全部分段渲染的联调验证。
